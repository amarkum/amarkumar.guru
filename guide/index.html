What to do in the interview

How an Amazon SDE II design round usually runs, what to say at each step, and what to avoid. Read this once the day before and once in the morning.

How the hour usually goes

  • 0–5 min
    Intros. Give a 60–90 second summary: current role, one project you owned, the impact with a number. Then stop.
  • 5–15 min
    Leadership Principles. Usually 1–2 behavioral questions (“Tell me about a time…”). Answer in STAR. Expect follow-ups like “What would you do differently?”
  • 15–25 min
    Requirements. The problem may be vague on purpose (“Design a logging framework”). Ask questions, list functional and non-functional requirements, write assumptions down.
  • 25–50 min
    Design. LLD: entities → classes → interfaces → core code. HLD: API → diagram → data model → deep dive. Expect a new requirement mid-way (“now add peak pricing”, “find the nearest store”).
  • 50–55 min
    Follow-ups. Concurrency, failure, scale, extensibility. “What if two users do this at once?” is very common.
  • 55–60 min
    Your questions. Always ask one or two (list below).

LLD vs HLD: what they check

LLD (class design + code)

  • Requirement gathering, then the class structure explained
  • Design patterns where they fit: Strategy, Factory, Observer, State, Composite/Specification, Builder, Chain of Responsibility
  • Effective Java: immutability, builders, interfaces over classes, enums, composition over inheritance, equals/hashCode, Optional over null
  • Readable, running code with few bugs
  • Handling follow-ups by extending, not rewriting

HLD (architecture)

  • Requirements and rough numbers
  • API design and data model
  • Diagram: clients, LB, services, cache, DB, queues, CDN
  • Deep dive on the hardest part, with trade-offs
  • Scale, consistency, failure handling, monitoring

Say this

  • “Can I take a minute to clarify requirements?”
  • “I'll assume X. Tell me if that's wrong.”
  • “I'll use a Strategy here so new pricing rules don't change existing code.”
  • “Two users could hit this at once, so I'll make the update atomic.”
  • “The trade-off is X vs Y. Given our requirements I'd pick X.”
  • “If this service fails, here's what happens…”
  • “I haven't used that, but here's how I'd reason about it.”
  • In stories: “I decided… I built… the result was 30% faster.”

Avoid this

  • Jumping into code before requirements
  • Long silences. Think out loud instead
  • Naming tools without a reason (“just use Kafka”)
  • “We did it” in stories without saying what you did
  • Bluffing about something you don't know
  • Arguing with hints. Hints are help
  • Saying “that's easy” or rushing
  • Criticising your current team or company
  • Bringing up salary or other offers in this round

Common follow-ups and how to answer

  • “Add this new feature.” Show it's a new class implementing an existing interface (Open/Closed).
  • “Two users at once?” Atomic conditional update, lock, or optimistic version check. Name which and why.
  • “Find the nearest X.” Geohash or quadtree, search own cell plus neighbours (how Uber does it).
  • “What if it's retried?” Idempotency key.
  • “What if this goes down?” Replicas, retries with backoff, fallback, dead-letter queue, alarms.
  • “How do you know it's healthy?” Metrics (latency, error rate), dashboards, alarms, logs with request IDs.

Questions to ask at the end

  • What does the team own in FinTech, and what's the hardest problem right now?
  • What does a great first six months look like for this role?
  • How does the team handle on-call and operational load?
